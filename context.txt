1. PROBLEM DESCRIPTION (PRINT DITHERING / FAINTNESS):
------------------------------------------------------------------------
When printing receipts to a monochrome 1-bit thermal printer (like TVS RP 3160 STAR) 
via Electron's `window.print()`:
- Small fonts (like 10px-11px JetBrains Mono) have thin stems.
- Chromium applies anti-aliasing (gray pixels) at the edges of the font.
- The thermal printer driver converts these gray pixels into a dotted dither 
  pattern to simulate gray, making the letters look faint or invisible.
- Colors like gray (#4b5563) used on slogan/operator details get heavily 
  dithered and print as faint, unreadable dot clusters.

------------------------------------------------------------------------
2. SOLUTION DETAILS (PRINT DITHERING FIX):
------------------------------------------------------------------------
We updated the `@media print` queries in `src/index.css` with the following 
optimizations specifically designed for 80mm/72mm thermal rolls:

- Solid Pure Black: Forced `color: #000000 !important;` on `.print-receipt-area` 
  and all nested elements (`.print-receipt-area *`). This prevents the browser 
  from outputting any gray shades, eliminating dithering on slogans/headers/footers.
- Bold Text: Forced `font-weight: 700 !important;` on all receipt text elements. 
  Bolder text increases the width of the printed stems.
- Stroke Thickness: Added `-webkit-text-stroke: 0.25px #000000 !important;` to 
  thicken text outlines slightly, ensuring the thermal print head burns solid lines.
- System Sans-Serif: Changed `font-family` during printing to standard system 
  sans-serif (`system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, Arial`) 
  which has simpler, cleaner, and thicker stems than JetBrains Mono at small sizes, 
  significantly enhancing Tamil and English legibility.
- Minimum Size: Forced a minimum highly readable print font-size of `12px` 
  via `.print-receipt-area * { font-size: 12px !important; }`, while preserving 
  the main shop title at `18px` via a helper class `.receipt-shop-name`.

5. PRODUCTION LOGGING SYSTEM (app.log WITH AUTO-ROTATION):
------------------------------------------------------------------------
To aid in remote debugging without cluttering the UI, we implemented a full 
production logging system:

- Log Storage Path: Saved to `app.log` in the application's root user data folder 
  (the same folder containing `database.json`, accessible in the OS filesystem at 
  `AppData\Roaming\PS Billing System\`). It cannot be accessed from the application UI.
- Lightweight Auto-rotation: Includes a strict limit check. If `app.log` exceeds **1 MB**, 
  it is renamed to `app.log.old` (replacing the previous `.old` file). This caps the 
  total log storage strictly at **2 MB** max, ensuring the app remains light and manageable.
- Recorded Events:
  - System Lifecycle: App start, startup platform metadata, user data folder paths, window loads.
  - IPC Operations: Window login/logout calls, database reads/writes (along with performance/speed 
    durations and data summary metrics), and silent print triggers.
  - Renderer User Actions: Exposes a `logMessage` bridge API. React components log logins, logout, 
    bill saves, bill deletions, visualizer open/close events, and CSV export triggers.
  - Crashes & Errors: Intercepts `uncaughtException` in the main process, `did-fail-load` window 
    load failures, and warnings/errors originating in the React console (`console-message` handler).

6. DUPLICATE ITEM CHECK DIALOG (PREVENT DUPLICATIONS):
------------------------------------------------------------------------
To prevent accidental duplications when a cashier scans or enters the same item 
code multiple times:

- Duplicate Detection: When adding a product (either by typing code directly and 
  pressing Enter, or selecting from the search overlay, or clicking search sidebar), 
  the app verifies if that item code is already added in another row.
- Choice Dialog Modal: If a duplicate is found, a dialog appears presenting 2 choices:
  1. "நிலவும் பொருளின் அளவை மாற்றவும் / Edit existing item quantity (Recommended)"
     Focuses the cursor onto the `qty` column of the existing product row so the 
     cashier can immediately adjust the weight/quantity. Clears the temporary duplicate row.
  2. "புதிய வரியாக சேர்க்கவும் / Add as a new row (new weight/qty)"
     Proceeds to add a new line with the duplicate code (useful for multi-weight slabs).
- Keyboard Navigation: The cashier can use the Arrow keys (Up/Down or Left/Right) to 
  change selection, press Enter to confirm the selected action, or press Escape 
  to dismiss/cancel.
- Logged Event: The selection choice is written to the production log for audit tracking.

13. DATA DURABILITY AUDIT & REPAIR (AUGUST 20, 2026):
------------------------------------------------------------------------
An audit of the Tauri app in `tari/` against the live shop database found the
billing flow sound but almost nothing protecting the money already recorded.
Six defects could destroy or corrupt saved bills through ordinary keystrokes.
All were fixed, verified against the real 1,850-bill database, and exercised in
the running app. Branch: `durability-fixes` (4 commits).

1. DEFECTS FOUND AND FIXED:

   a) Deleting one bill deleted up to 120 (`SalesHistory.jsx`)
      - Delete matched on `invoiceNo`, which is NOT unique. The 1,850 imported
        bills share only 138 distinct numbers; 1,817 of them (98.2%, Rs11,24,864)
        sat on a duplicated number. Deleting #504 removed 120 bills at once and
        restored stock for only one of them.
      - FIX: every bill now carries an immutable `id`. `handleDeleteTransaction`
        takes the transaction object and matches on `id`. Verified: a sweep over
        all 1,850 bills removes exactly one, every time.

   b) Invoice numbers collided by design (`BillingDashboard.jsx`)
      - `getNextBillNumber()` returned `todayTx.length + 1`. Deleting a bill
        handed its live number to the next customer.
      - FIX: numbers come from `settings.billCounter = { date, next }`, which is
        written in the SAME `onUpdateDatabase` call as the bill. Daily reset is
        preserved (#1 each morning) but a number is never reissued. If the
        counter is missing or stale it falls back to max(today invoiceNo) + 1,
        so a number already on a printed bill is never handed out twice.

   c) Every historical bill reprinted as "Rs NaN" (`PrintReceiptModal.jsx`)
      - The August import wrote line items as { rate, amount, total }; the app
        reads { overridePrice, totalPrice, priceType }. All 1,850 bills were
        affected - every line printed RsNaN, only the footer total was right.
        Legacy items also had no `priceType`, so weighed goods hit the
        `parseInt` branch and a 0.5 kg line printed as quantity 0.
      - FIX: new `src/utils/normalize.js` converts either shape to one canonical
        shape, applied inside `readDatabase()`. PrintReceiptModal coerces every
        figure through a `money()` helper so a malformed item prints 0.00.

   d) Viewing an old bill and pressing F10 zeroed it (`BillingDashboard.jsx`)
      - F11/F12 guarded against read-only view mode; F10 did not. PageUp then
        F10 rewrote the totals from the missing `totalPrice`, turning Rs276.00
        into Rs0.00 with no confirmation.
      - FIX: F10 now carries the same guard. Also added `e.repeat` rejection on
        F10/F11/F12 and an `isSavingRef` in-flight lock, so a held or
        double-tapped key cannot commit two bills.

   e) No backups, and a power cut could truncate the only copy (`lib.rs`)
      - `db_write` used temp+rename (correct shape) but never flushed before the
        rename, used a fixed `database.json.tmp` shared by concurrent commands,
        and no copy of the database existed anywhere.
      - FIX: `write_file_atomic()` calls `sync_all()` before the rename and uses
        a temp name carrying pid + nanosecond stamp. A `DbLock(Mutex)` in Tauri
        state serialises writes. `refresh_backups()` keeps
        `backups/database-YYYY-MM-DD.json` for 7 days plus
        `database-monthly-YYYY-MM.json` kept indefinitely. `db_read` no longer
        seeds over a corrupt live file - it recovers from the newest parseable
        backup, renames the bad file to `database.corrupt.<stamp>.json`, and
        errors rather than seeding if no backup is usable.

   f) The shipping app was not in version control
      - `.gitignore` ended with `tari/`; `git ls-files tari` returned nothing.
        Only the stale Electron copy in `src/` was tracked, diverged by 1,296
        lines. (This is also why `oxlint` reported "No files found to lint" when
        run inside `tari/`.)
      - FIX: `tari/` is committed. `.gitignore` now excludes only build output
        (`tari/src-tauri/target/`, 1.4 GB) and live shop data, and explicitly
        re-includes the app artwork (`!tari/public/*.png`,
        `!tari/src-tauri/icons/**`) which the blanket `*.png` / `*.ico` rules
        had been silently excluding - without those a fresh clone cannot build.
        The superseded `src/`, `dist-desktop/` and `dist-installer/` copies were
        deleted in a separate commit.

2. WHOLE-RUPEE ROUND-OFF (BEHAVIOUR RESTORED):

   Discovered while verifying the edit path: netTotal = round(gross - discount
   + rent + coolie) reproduces ALL 1,850 legacy bills exactly, and the old
   FoxPro export carries a non-zero `roundOff` field on exactly 752 of them.
   The shop has always billed in whole rupees; the new app was producing paise
   totals, and re-saving an old bill drifted it by up to 50 paise.

   - `calculateRawNetTotal()` holds the unrounded figure; `calculateNetTotal()`
     returns `Math.round()` of it; `calculateRoundOff()` is stored on the bill.
   - The receipt prints a Round Off line when it is non-zero.
   - Money is rounded to paise via `round2()` on save, so values like
     130.00000000000003 can no longer reach the database.

3. UNIT / PRICE-TYPE REPAIR:

   726 of 1,803 products in `IM012026.DBF` point at a unit row that no longer
   exists in `UN012026.DBF` (623 dangling codes + 103 blank). Those unit rows
   were deleted from the FoxPro unit master years ago while products kept
   referencing them - this is a hole in the source data, NOT an import bug. The
   11 missing codes appear in none of the three legacy installs (SMS, SMS1,
   Sms3), and the product master weight flags (`IWEIGHT`, `WF`, `WGTAA`, `RBW`,
   `MINWEIGHT`) are uniformly unset on every product, so nothing can recover
   them.

   `import_old_data.py` fell back to `units_map.get(code, "piece")` and
   `priceType = "Quantity" if unit in (kg, litre) else "Fixed"`, so 620 became
   Fixed - meaning `Math.round()` on quantity, and no slab pricing. Real
   consequence: 2.5 kg of IDLY RICE became 3 kg at the counter.

   - REPAIRED: 29 products the sales history PROVES were sold in fractions were
     set to `priceType: 'Quantity'`. Where the unit was also an unresolved code,
     it became `kg` (17 products); where it already read as a real unit, the
     unit was left alone (12 products).
   - NOT GUESSED: the "unit is kg/litre implies Quantity" rule was rejected -
     64 products are labelled `litre` including rice and flour sold by the bag,
     so the unit column itself cannot be trusted as evidence.
   - The remaining unresolved units are now VISIBLE rather than silently wrong:
     new `src/utils/units.js` renders them as "not set" in ProductManager and
     "?" in the billing grid. The unit dropdown carries a synthetic option so
     the current value is never invisible, and picking kg/litre now sets
     `priceType: 'Quantity'` automatically.

4. NEW FILES:

   - `tari/src/utils/normalize.js`  - canonical transaction/line-item shape,
     `round2()`, `indexProducts()`, `normalizeDatabase()`. `unit` and
     `priceType` are read from the product master first, so repairing a product

   - `tari/src/utils/units.js`      - `UNIT_OPTIONS`, `isUnresolvedUnit()`,

9. SLAB OFFSET SIGN CORRECTION (found after the audit, same day):

   SYMPTOM: JEERA (M47) at 50g billed Rs13.50. The old software bills Rs24.50.

   CAUSE: the old system stores its slab differential in `IM012026.DBF` as
   WQ1..WQ4 (quantities) and WRATE1..WRATE4 (differentials), and applies it as

       effectiveRate = SRATE - WRATE

   M47 has SRATE 380 and WRATE1 -110, so the shop charges 380 - (-110) = 490/kg
   and 50g costs Rs24.50. The Aug 18 slab ingestion copied WRATE straight into
   `offset`, but the app applies

       effectiveRate = sellingPrice + offset

   giving 380 + (-110) = 270/kg and Rs13.50 - undercharging by Rs11 on every
   50g sale of an expensive spice. Some products were worse: AACHIKULAMBU50GM
   (116) computed a NEGATIVE rate of -Rs2/kg.

   NOTE: the slab values are in the W-series (WQ/WRATE), not the S-series
   (SQ/SRATE) that section 12 above refers to. On M47 the S-series is all
   zeros. Anything re-importing slabs must read WQ1..WQ4 / WRATE1..WRATE4 and
   NEGATE the rate, because the app adds the offset where FoxPro subtracts it.

   `tari/import_old_data.py` in this repo is NOT the culprit - it always writes
   `"slabs": []`. The script that ingested the slabs on Aug 18 is not in the
   repo. If it resurfaces, this is the line to fix.

   EVIDENCE: checked against the 1,850 real bills, which record what customers
   were actually charged. Of the 287 slab bands with sales history:

     - 57 were wrong before and are correct after the negation
     - 0 were broken by the negation
     - 120 were already correct (offset 0, unaffected)
     - 110 match neither, because the base selling price has changed since
       those July sales - not a slab problem

   M47 after the fix, against the old software: 50g Rs24.50, 100g Rs49.00,
   250g Rs95.00, 500g Rs190.00, 1kg Rs380.00 - every band matches.

   FIX APPLIED: `tari/scripts/fix_slab_offsets.mjs` negates the offsets of the
   75 affected products. It only touches slabs that still match the FoxPro
   source exactly, so any slab edited by hand in the app since the import is
   left alone (0 such products at the time it ran). It backs up first, and
   aborts if the correction does not improve agreement with real sales.

       node tari/scripts/fix_slab_offsets.mjs --dry-run
       node tari/scripts/fix_slab_offsets.mjs

   The app code was NOT changed. `sellingPrice + offset` stays the convention,
   because that is what the Product Manager screen shows and what a shopkeeper
   typing a new slab by hand would expect. Only the imported data was wrong.

   CONSEQUENCE FOR PRICES: 75 products now charge MORE at small quantities than
   the app was charging before this fix - which is what the shop has always
   charged. Worth spot-checking a few against the old software before a busy
   day.
